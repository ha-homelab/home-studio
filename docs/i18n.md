# Languages and translation contributions

Home Studio's drawing editor has 24 language packs. Choose a language in the
editor header. The initial choice follows your browser's language when supported;
an explicit choice is remembered by this browser. English is the fallback.

The translated surface includes drawing tools, the item library, catalog names,
palettes, patterns, the property inspector, dialogs, status messages, and
accessibility labels. Arabic, Hebrew, and Persian use right-to-left text. The
plan's coordinates, keyboard shortcuts, dimensions, and the 3D camera retain
their usual meaning in every language.

[Localized README quick starts](translations/README.md) explain the drawing and
installation path. The detailed illustrated guide, technical documentation,
compiler diagnostics, and installed Home Assistant viewer currently remain in
English. A language pack is not a translation of user-entered room names, notes,
Home Assistant entity IDs, or imported project content. Those values must never
be changed by switching languages.

## Storage, privacy, and performance

- Translations are bundled with the project. No text or drawing is sent to a
  translation service.
- English loads with the editor; other packs load from this same website only
  when selected. A visitor does not download every language at startup.
- Locale module names come from an explicit allowlist, not an arbitrary URL.
- Language preference is independent of the project JSON. The same exported
  project works in every language and changing language does not create an edit.
- The language setting uses local browser storage. If storage is unavailable,
  the editor must continue to work without persistence.
- Translated text is inserted as text, never evaluated as HTML. Placeholders are
  interpolated without interpreting project values as markup.

## Add or improve a language

1. Use `planner/locales/en.js` as the canonical key list. It contains complete
   English messages plus stable `model.*`, `category.*`, `palette.*`, and
   `pattern.*` catalog keys.
2. Create `planner/locales/<code>.js` with `export default { ... }`. Translate
   values, never keys. Preserve named placeholders such as `{name}` and `{count}`
   exactly, even when the sentence puts them in a different order. Keep `JSON`,
   `Python`, `Home Assistant`, commands, code, and entity identifiers recognizable.
3. Add the language's native name to `planner/locales/index.js`. Use a valid
   language tag and add `dir: 'rtl'` only for right-to-left languages.
4. Add its module to the explicit public-file allowlist in
   `scripts/validate-site.py`. Add a localized README quick start and link it from
   `docs/translations/README.md`.
5. Run the translation contract checks, public-site validator, and browser i18n
   checks. Inspect long labels, the item library, dialogs, and a narrow viewport.
   Verify a project exports identically before and after language switching.

```sh
node scripts/test-i18n.mjs
node scripts/test-validation-i18n.mjs
python3 scripts/validate-site.py
npm ci --ignore-scripts
npx playwright install chromium
node scripts/test-i18n-browser.cjs
```

Keep messages as complete sentences instead of concatenating translated pieces.
Do not translate the DOM automatically: that can corrupt a user's room names or
code examples, and makes language changes hard to reverse. Validation guidance carries structured message keys and named values; only explicitly
marked field labels are translated, while room names and identifiers stay literal.
The original English error remains available for logs and compiler parity.

New dynamic UI needs
an explicit translation call; new static UI needs an explicit translation marker.

## Quality and fallback policy

Automated checks verify key coverage, placeholders, module validity, public
packaging, and core browser interactions. They cannot certify idiomatic wording
in every language. Native-speaker corrections are welcome; report the language,
screen, current wording, and suggested wording using a fictional example.

All advertised packs must contain the complete canonical key set. English
fallback is still necessary for a failed download or an older cached pack; it
must not be used to advertise an empty or partially translated language pack.
Technical error details from imported files or the browser may remain in their
original language after a translated explanation.
