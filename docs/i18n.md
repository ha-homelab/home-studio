# Languages and translation contributions

Home Studio's drawing editor has 24 language packs. Choose a language in the
editor header. The initial choice follows your browser's language when supported;
an explicit choice is remembered by this browser. English is the fallback.

The translated surface includes drawing tools, the item library, catalog names,
palettes, patterns, the property inspector, dialogs, status messages, and
accessibility labels. This includes Site & roof, Neighborhood, neighbor appearance,
and native editor map status and recovery messages. Switching languages keeps
feature names, coordinates, and all exported project data unchanged. The optional
AI planning panel currently identifies its interface as English.

Arabic, Hebrew, and Persian use right-to-left text. The
plan's coordinates, keyboard shortcuts, dimensions, and the 3D camera retain
their usual meaning in every language.

[Localized README quick starts](translations/README.md) explain native HA
installation, drawing, saving, and publication. The illustrated guide and
installation pages lead with the same native workflow in English. Their
localized quick guides appear lower down and cover the optional separate-editor
and portable-toolkit workflow; command examples remain literal. Detailed
reference text and screenshots remain in English and are labelled accordingly.

The installed viewer translates everyday navigation, placement fields, basic
device states, and common editing feedback in the same 24 languages. Advanced
signal/receiver diagnostics, curtain recovery explanations, host-panel recovery
messages, detailed Home camera gesture hints, technical documentation, and
command-line diagnostics remain in English. A language pack is not a translation
of user-entered room names, notes, Home Assistant entity IDs, or imported project
content. Those values must never be changed by switching languages.

## Storage, privacy, and performance

- Translations are bundled with the project. No text or drawing is sent to a
  translation service.
- English loads with the editor; other packs load from this same website only
  when selected. A visitor does not download every language at startup.
- Locale module names come from an explicit allowlist, not an arbitrary URL.
- Language preference is independent of the project JSON. The same exported
  project works in every language and changing language does not create an edit.
- The language setting uses local browser storage. If storage is unavailable,
  the editor must continue to work without persistence.
- Translated text is inserted as text, never evaluated as HTML. Placeholders are
  interpolated without interpreting project values as markup.
- The generated viewer embeds a separate compact dictionary for its everyday
  controls. It neither downloads the furniture catalog translations nor calls
  a translation endpoint. Its language selection works offline, including in
  Home Assistant's sandboxed frame.

The viewer compiler stores translation keys once and reconstructs the complete
dictionary when its module loads. Missing entries keep the English fallback;
empty strings and literal keys remain unchanged. This encoding changes only
the bundled messages, not model JSON, source catalogs, or language behavior.
`python3 scripts/test-viewer-locales.py` checks every language, safe script
embedding, and the size of the actual rendered viewer.

## Language across the workflow

Editor and help links carry the chosen language in `?lang=` while retaining
their anchors. The language is also remembered on that website when browser
storage is available. This preference does not belong to the project file.

The Home Assistant panel has a separate origin and authentication boundary.
It defaults to the HA profile language; selecting a language in the viewer
overrides that default. The host also accepts an explicit supported `?lang=` value for the current
load; it takes precedence over the saved choice until a different language is
selected. Keep the URL parameter in a bookmark when that initial override is
intentional. The trusted panel stores the preference under
`home-studio.language.v1` and restores it on the next floor load. The sandboxed
viewer uses its existing MessagePort to communicate this preference. It cannot
read the host's storage or credentials. A language choice does not save an
inventory, send a device command, or restart the renderer.

An explicit choice lasts for the current session even if storage is denied.
After reloading without storage, the default comes from HA or the browser again.
Regional language tags resolve to supported packs; unsupported languages fall
back to English. Numeric geometry, identifiers, commands, and the canvas retain
left-to-right coordinates even in Arabic, Hebrew, and Persian.

## Add or improve a language

1. Use `planner/locales/en.js` as the canonical key list. It contains complete
   English messages plus stable `model.*`, `category.*`, `palette.*`, and
   `pattern.*` catalog keys.
2. Create `planner/locales/<code>.js` with `export default { ... }`. Translate
   values, never keys. Preserve named placeholders such as `{name}` and `{count}`
   exactly, even when the sentence puts them in a different order. Keep `JSON`,
   `Python`, `Home Assistant`, commands, code, and entity identifiers recognizable.
3. Add the language's native name to `planner/locales/index.js`. Use a valid
   language tag and add `dir: 'rtl'` only for right-to-left languages.
4. Add its module to the explicit public-file allowlist in
   `scripts/validate-site.py`. Add a localized README quick start and link it from
   `docs/translations/README.md`.
5. Run the translation contract checks, public-site validator, and browser i18n
   checks. Inspect long labels, the item library, dialogs, and a narrow viewport.
   Verify a project exports identically before and after language switching.

```sh
node scripts/test-i18n.mjs
node scripts/test-validation-i18n.mjs
python3 scripts/validate-site.py
npm ci --ignore-scripts
npx playwright install chromium
node scripts/test-i18n-browser.cjs
node scripts/test-help-i18n.cjs
node scripts/test-viewer-i18n.cjs
python3 scripts/test-viewer-locales.py
node --test scripts/test-panel-language.cjs
python3 scripts/build-panel-locales.py --check
```

Keep messages as complete sentences instead of concatenating translated pieces.
Do not translate the DOM automatically: that can corrupt a user's room names or
code examples, and makes language changes hard to reverse. Validation guidance carries structured message keys and named values; only explicitly
marked field labels are translated, while room names and identifiers stay literal.
The original English error remains available for logs and compiler parity.

New dynamic UI needs
an explicit translation call; new static UI needs an explicit translation marker.

## Quality and fallback policy

Automated checks verify key coverage, placeholders, module validity, public
packaging, and core browser interactions. They cannot certify idiomatic wording
in every language. Native-speaker corrections are welcome; report the language,
screen, current wording, and suggested wording using a fictional example.

All advertised packs must contain the complete canonical key set. English
fallback is still necessary for a failed download or an older cached pack; it
must not be used to advertise an empty or partially translated language pack.
Technical error details from imported files or the browser may remain in their
original language after a translated explanation.

## Viewer and help contributions

The viewer's canonical messages live in `viewer-locales/en.json`, with native
language names in `viewer-locales/index.json`. Keep each JSON dictionary's keys
and named placeholders identical. `viewer-i18n.js` supplies interpolation and
explicit DOM markers. The compiler bundles these messages separately from the
editor packs. The authenticated host's supported codes must match the manifest;
`scripts/test-panel-language.cjs` enforces that boundary.

The localized quick route reuses editor terminology and keeps its small set of
additional explanations separate. Never translate commands or insert translated
HTML. Keep the original English reference accessible without JavaScript.

## Host controls and Dry run messages

The host header, Dry run button/title/status, connection notices, menu
accessibility label, reload label, and common device-command validation or error
messages use the same 24 locales as the viewer. Pending or last-error feedback
keeps a stable message key and parameters, so it can be displayed in the newly
selected language without issuing another command. Raw upstream error detail
and advanced inventory-recovery instructions remain in English.

`viewer-locales/*.json` is the canonical text source. The explicit `KEYS` list in
`scripts/build-panel-locales.py` selects the compact host subset and embeds it
inside `custom_components/home_floorplan/static/panel.js`. After changing a host
message, update every dictionary and the key list when necessary, then run:

```sh
python3 scripts/build-panel-locales.py
python3 scripts/build-panel-locales.py --check
```

The generated block must not be edited by hand. The authenticated host loads no
translation URL and does not expose credentials to the iframe. Right-to-left
header text does not mirror the floorplan. Changing language never changes the
Dry run guard or a physical device. The [Dry run reference](dry-run.md) documents
its independent storage and command policy.

The [repository-local wiki](wiki/Home.md) links operating and troubleshooting
guides. [README quick starts](translations/README.md) contain localized
introductions and Dry run guidance for every supported locale; detailed
engineering references and source SVG diagrams remain English.
