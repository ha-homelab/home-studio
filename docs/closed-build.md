# Closed HA packages in public release orchestration

`closed-build.yml` is a reusable **job of the public release pipeline**. Its
inputs contain public release references and an optional opaque request ID.
Private source, archives, hashes, and detailed diagnostics stay in closed object
storage. The first package contract is `ha-home-python-v1`; it covers Python
geometry, exact component composition, and site contracts. It does not claim
browser, device, or standalone gateway-image acceptance.

The release pipeline is generated by the CI toolkit. Add or change its closed
branch in that generator, then render it here. Do not hand-edit the generated
pipeline. Its existing public gate stays unchanged; an enabled closed build must
succeed before candidate/final publication. Stable promotion validates already
accepted bytes without rebuilding them.

## Trust and execution

The worker is restricted to the exact Home Studio repository and owner IDs,
`refs/heads/main`, the release-pipeline caller, and push/schedule/manual release
events. It requires a GitHub-hosted runner and rejects debug mode. Configure the
`closed-build` environment with an explicit main-only deployment policy and
protect workflow, wrapper, toolchain policy, and key changes through review.
The workflow declares no caller secrets and no write permissions.

`prepare` downloads the public digest-pinned HA/Python image and approved public
dependency commits **before the step that receives closed credentials**. The
image and dependency revisions are reviewed in `.closed-build-policy.json`.
The Dockerfile documents the image contract; private contents never enter an
image build or image layer. A signing request cannot select a different image.

The host validates exact run/attempt, producer identity, immutable Actions ZIP
digest and artifact creation time before extracting public artifacts. It then
checks the frozen version plan, declared version metadata, and existing unsigned
staging receipts against the exact source-commit policy and actual payloads.
These receipts are hash bindings, not signatures. A
published-release resolver runs without closed credentials and supplies the
same validated public context for rebuild/promotion.

The private bundle is verified and decrypted by the host. Only a fixed private
Python entrypoint executes, inside a container with no network, user 65532,
read-only tooling/input, dropped capabilities, no-new-privileges, no Docker
socket, and no host credentials. Memory, CPU, process count, individual file
size, scratch, output, log, and execution time are bounded. A second equally
isolated container holds the 128 MiB output tmpfs alive while the host checks its
two-file inventory and copies it out. All container streams are captured into a
bounded private log; Docker's persistent log driver is disabled.

The compressed home package has a separate 128 MiB transport limit; each
extracted scene file remains limited to 64 MiB and total expansion to 512 MiB.
Worker acceptance metadata is limited to 100,000 bytes. The outer candidate,
including its metadata and trusted installer, must also fit the envelope's
128 MiB plaintext limit. The output tmpfs and outer-container overhead can
therefore reject a package near the transport ceiling.

The host rejects traversal, links, special files, duplicate archive paths,
oversized expansion, unexpected output, and any package that changes or omits
an exact staged public component file. It supplies the installer from the
validated public source archive, rather than accepting a worker-selected one.

GitHub and its trusted host still process plaintext. This arrangement prevents
ordinary worker exfiltration and accidental publication; it is not confidential
computing against the host, provider, administrators, or approved build code.

## Transport and approval contract

`scripts/closed_envelope.py` is the shared transport implementation. Keys are
base64-encoded raw 32-byte X25519 or Ed25519 keys. A fresh ephemeral X25519 key
and HKDF-SHA256 derive each AES-256-GCM key. The nonce, recipient/signer
fingerprints, purpose and schema are authenticated. Ed25519 signs the complete
envelope; the receiver verifies the pinned signer before decrypting. Input,
candidate, diagnostic and acceptance envelopes have distinct purposes. The
host-only cryptography dependencies are version- and hash-pinned for Python
3.12 on Ubuntu x86_64.

An input envelope encrypts a gzip tar containing a curated source tree and
`closed-build.json`. That manifest includes:

- `schema: 1`, an opaque `request_id`, and a SHA-256 `files` inventory excluding
  the manifest itself;
- `entrypoint: scripts/closed-build-entry.py`, `acceptance_policy:
  ha-home-python-v1`, the exact `worker_image`, and `build_mode` of
  `package-only` or `rebuild-preserve`;
- `original_core_lock`, which must match the archived lock without alteration;
- either an exact `target` containing `source_sha`, `plan_sha256` and `payloads`,
  or a constrained `target_policy`.

The signed target policy pins one exact public source SHA, base version,
repository/owner IDs, approved dependency locks, and allowed `beta`/`rc`/`nightly`
channels. Only the frozen plan and its payload hashes are concretized by the
trusted host after public qualification. It is not permission to follow future
main revisions. A new source SHA requires renewed operator authorization.
Stable uses accepted RC bytes and does not use this build delegation.

The entrypoint receives `--public-source /public/source`,
`--public-component /public/component`, `--dependency-root
/public/dependencies`, `--context /context/build.json`, and `--output
/output/home-package.tar.gz`. The context has `public`, `original_core_lock`,
and an explicitly authorized `effective_core_lock`. Each dependency snapshot
has a `dependency.json` binding its original repository/commit and file hashes.
No runtime Git fetch or private checkout is needed.

The worker returns exactly `home-package.tar.gz` and `acceptance.json`.
Acceptance has `schema: 1`, `passed: true`, and a `checks` list containing
`package` and `site-contracts`; `rebuild-preserve` also requires `geometry`.
Additional closed diagnostic fields are allowed. A package-only result never
claims that its geometry was rebuilt.

The encrypted candidate tar contains `candidate.json`, `home-package.tar.gz`,
and the host-supplied `install-home-assistant.py`. The signed candidate binds
input/intent/policy hashes, original/effective locks, concrete public context,
worker image, checks, package and installer SHA-256/size, and closed build run
ID/attempt. `public.run_id/run_attempt` identify the **public source producer**;
root `build_run_id/build_run_attempt` identify the **closed build**, whose exact
workflow source revision is `build_source_sha`. These may
differ. Upload uses `<request>/<build-run>-<attempt>.candidate.json` and
`If-None-Match: *`; an existing candidate is never overwritten.

A candidate is not install approval. A separately pinned operator signs an
acceptance record only after actual matching public publication and successful
exact source/closed-build attempts. Record separate `qualification.source_run`
and `qualification.closed_build_run` objects (`id`, `attempt`, `latest_attempt`,
`conclusion`), plus published release identity and exact `public` context.
A later stable promotion run is a distinct proof. An unpublished/superseded
plan or a generic green workflow cannot satisfy this contract.

The accepted record also requires `site_acceptance`, binding the package digest
to a separately signed `site-canary-passed` receipt with `checks.actual_ha` and
`checks.browser` both true, plus the evidence and original receipt digests.
The operator's acceptance client verifies that receipt before retaining it.
Python package checks and transport-only fixtures cannot replace this evidence.

Stable validation reads an operator-signed acceptance envelope encrypted to
the CI input recipient. It verifies matching source/plan/payloads and both run
identities, rechecks the closed build's current successful run and latest attempt,
reads the exact stored candidate ciphertext, and checks its digest
and pinned signature without requiring the deployment decryption key. The
private deployment client retains its own signed acceptance record and can
install already accepted immutable bytes after Actions evidence expires.

## Protected environment configuration

`CLOSED_INPUT_READ_URL` is a fixed-object HTTPS read capability for the approved
input envelope. `CLOSED_OUTPUT_WRITE_URL` and `CLOSED_OUTPUT_READ_URL` are
separate narrowly scoped prefix capabilities ending with `/`; listing should
be disabled. `CLOSED_ACCEPTANCE_READ_URL` reads the fixed signed acceptance
envelope for stable validation. Capability URLs are bearer secrets. HTTP,
embedded user credentials, nonstandard ports, URL fragments and redirects are
rejected; private values never enter subprocess arguments.

`CLOSED_INPUT_DECRYPT_KEY` and `CLOSED_INPUT_VERIFY_KEY` decrypt/authenticate
operator requests. `CLOSED_OUTPUT_ENCRYPT_KEY` encrypts to the deployment
recipient; `CLOSED_OUTPUT_SIGN_KEY` signs candidate provenance. Never copy the
deployment recipient's private key into CI. Key rotation requires explicit
trust updates; fingerprints supplied by an envelope never choose a trust root.

No closed contents are uploaded as Actions artifacts, cache entries, SARIF,
summaries, public release assets, packages, Pages, or public transparency-log
attestations. Detailed failures are encrypted to closed diagnostics. Public
stdout contains fixed status codes only. Interrupted runners may lose
diagnostics; confidentiality does not depend on cleanup succeeding.

## Fresh admission before a closed rebuild upload

For `action=rebuild` only, a long build can outlive its initial storage check.
Immediately before uploading the encrypted candidate, the host writes a small
encrypted and signed `upload-intent` to the existing output prefix and waits up
to 120 seconds for an operator `upload-permit`. Both envelopes are limited to
8 KiB. They bind the request, workflow source, run and attempt, input digest,
target object, ciphertext digest and size, exact rebuild operation and worker
job, output capability digest and a fresh random nonce. No additional Actions
secrets, list access or broad OCI credentials are given to the worker.

The reviewed local operator authenticates the live run and collects a complete
version-inclusive inventory and regional Limits response. Available space is
the smaller measurement. The required headroom is the maximum candidate size
plus 144 MiB of remaining reserve and 8 KiB for the not-yet-stored permit.
Unknown, incomplete or insufficient capacity produces no permit. Earlier
approval or a previous green snapshot is insufficient. The permit expires
within 30 seconds of both issuance and the start of the snapshot, whichever
is earlier.

The rebuild verifies the operator signature, exact bindings and freshness,
then makes one create-only candidate PUT. Its socket timeout is bounded by
remaining permit life; a response after expiry is rejected. This is admission,
**not a storage reservation** or server-enforced expiry. Concurrent writers can
still consume capacity, and a late or interrupted PUT may have created an
object. Reconcile the exact object and journal; do not retry, renew or overwrite
automatically. No private payload or encrypted control is staged in Actions
artifacts.

A changed workflow/helper needs a newly prepared rebuild request with pinned
helper hashes. Retain old request evidence and keys rather than rebinding an
exported request. Start the coordinator immediately after approving the rebuild;
browser-only approval without its permit loop makes the rebuild time out.

Normal `action=build` releases retain their existing single create-only upload,
without an intent or permit. Migrating their manual, push/beta and
schedule/nightly coordinators is tracked in [issue #97](https://github.com/ha-homelab/home-studio/issues/97).
`action=validate` continues to verify and reuse accepted bytes without a new
candidate upload. Retained accepted candidates remain installable under their
original protocol and acceptance proof.

## Validation and recovery

Run `python3 scripts/test_closed_build.py` and
`python3 scripts/test_closed_upload_control.py` for transport, upload admission, source policy,
archive safety, exact component and failure-output tests. With a prepared
public image and an available Docker daemon, set `CLOSED_DOCKER_TEST=1` for
the real synthetic container success/failure and isolation checks. The public
package workflow runs both; all fixtures are fictional and use temporary keys.

For local Colima checks on macOS, select the intended daemon with an explicit
`DOCKER_HOST` socket and set `TMPDIR` to a directory under its shared `/Users`
tree. The macOS default `/var/folders` temporary directory may not be available
for container bind mounts. Create the shared temporary directory before running
the checks; no container isolation settings need to change.

For a real hosted storage trial, `scripts/closed_synthetic.py` takes the public
resolver's context plus local key and canary files and creates a fictional
encrypted input. Its success, failure, two-second timeout, and invalid-signature
modes exercise the same public workflow. Keep unique canaries outside the
repository and scan every public output surface after each run. The helper
does not upload, dispatch, or touch an actual home. These candidates use the
distinct `transport-canary-v1` policy and `synthetic: true`; they prove transport
and containment only. Production acceptance pinned to `ha-home-python-v1`
must reject them. Normal home-package validation also rejects fixture reports.

Tests do not establish a production HA restart, browser canary, physical device
behavior, or cloud ACL correctness. Those are distinct rollout checks. In
particular, the presence of HA dependencies in the image is not evidence that
HA acceptance has run.

Use fresh dispatch after fixing an interrupted/failed attempt. Keep the
client's durable opaque request journal and respect deliberate cancellation.
The release generator must preserve requests with its queue policy, while the
client handles overflow/retry; an existing candidate cannot be overwritten to
repair an old source-run attempt. Published-release rebuilding still requires
currently retrievable valid immutable public evidence.
